核心设计

不是寻找“能改的地方”，而是证明“删掉以后更好”。

Find Simplifications 把宽泛的简化请求转成少量、高置信、可验证的候选。它关注净减少、行为边界和维护成本，而不是代码风格、抽象搬家或行数竞赛。

唯一判断标准
证据足够 + 净维护面下降 + 放弃的行为可接受 + 验证路径明确

从项目专用经验，提炼为仓库无关方法

参考版本提供了有效判断经验；新版本只保留可迁移的方法，并把目录、语言、设计文档和验证命令全部改为运行时发现。

五阶段主逻辑

每一步都会缩小不确定性。候选只有经过消费者证明、历史核对和净收益权衡，才进入最终结果。

阶段 01 · Scope

先确定“找什么”与“能做什么”

区分只读发现、书面提案和直接实施；同时识别项目是否存在外部兼容承诺，避免把仓库内零调用误判成公开 API 已死亡。

输入用户措辞、仓库规则、发布状态
关键门槛权限和兼容范围必须明确
输出审计边界与证据来源

候选不是“看起来复杂”

Skill 同时定义进入标准和否决条件，让报告更短，也让保留复杂度的理由变得可见。

✓

进入候选集

  • 没有有意义的生产消费者，或仅由过时测试和文档维持。
  • 多个状态、事件、缓存或回调表达同一事实。
  • 抽象、配置或兼容路径没有当前产品所有者。
  • 平台能力或健康依赖能真正删除自研实现和专属测试。
  • 移除范围、行为损失和最小验证路径都能说清楚。
×

拒绝或降级

  • 当前生产调用者确实需要该行为。
  • 公开 API 的外部兼容情况仍然未知。
  • 方案只是移动代码、增加包装或制造另一层抽象。
  • 删除实质上是未经授权的产品决策。
  • 依据只有行数、复杂度指标、一次静态扫描或个人风格偏好。

一个候选如何穿过证据链

以前向测试中发现的空启动钩子为例：不是因为函数很短而删除，而是因为完整证据证明它没有行为和所有者。

发现

启动入口调用 Test()

函数体只有注释，但“看起来没用”仍不是结论。

证明

全仓只有一个调用点

没有配置、动态注册、测试或文档消费者。

核对

历史标记为未启用实验

原始动机不是产品能力，也没有兼容承诺。

闭环

删除入口、声明与实现

最小验证是重新构建并执行一次启动冒烟测试。

最终结论高置信简化：完整删除无效启动路径，而不是重命名、封装或保留空兼容层。
